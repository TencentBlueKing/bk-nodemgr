# bk-nodemgr README Logic-First

## Overview

本 skill 用于把 bk-nodemgr 的“代码导览”改写为围绕读者问题的 README 或逻辑说明。

核心标准：先确定文档所属层级，再决定信息深度；内容锚定当前 artifact 的职责，章节回答读者问题，结论保留成立条件，验收检查语义而非渲染结果。

让读者快速回答：

1. 这个模块在解决什么问题？
2. 哪些规则或关系决定结果？
3. 每个分支在什么条件下触发？
4. 返回、完成、失败分别意味着什么？

默认写作风格：**中文主述 + 英文 technical terms**（如 `scope`, `intersection`, `policy`, `PermissionDenied`）。

代码层 README 以自洽为原则：可以向下依赖，不许向上依赖。

## When to Use

用于 README 或逻辑说明类任务：

- 用户要求“写 README / 重写 README / 文档化逻辑”
- 用户强调“不要讲代码细节，要讲逻辑”
- 用户要求解释业务流程、分支、状态或行为边界
- 用户要求“去掉废话、保留高信息密度内容”

不适用：

- API reference、changelog、PR 描述、Issue 或代码审查；由对应 skill 决定格式
- 只改一两句文案，不涉及逻辑结构

配合 `bk-nodemgr-audience-boundary` 处理读者正文与作者核验事项；本 skill 不重复定义该边界。需要选择文档位置时，先用 `bk-nodemgr-agent-information-architecture`。

## Mandatory Workflow

1. **Policy Alignment**
   - 先读取相关 `AGENTS.md` 的语言和文档约束。
   - 按适用规则的优先级处理要求；仅在影响当前任务的歧义无法消除时询问。
   - 阅读目标模块和同类文档，遵守目标 artifact 的格式，不用本 skill 覆盖专用模板。

2. **Reader And Artifact Anchor**
   - 先区分 README 类型：文档层 README（如 `docs/**`）按文档任务组织，可跨层说明；代码层 README（代码目录内的 README）以自洽为原则。
   - 代码层 README 自洽：只凭本目录及其向下依赖即可读懂；可以引用或链接本模块依赖的下层能力，不许引用、链接或描述上层调用方及其业务场景。
   - 明确读者、原始问题、读完需要作出的判断或操作。代码层 README 偏概览，通常回答：是什么、负责什么、不负责什么、使用前提是什么。
   - 从本模块源码、契约和下层依赖抽取稳定事实；只保留影响读者判断或集成的内容。
   - 业务锚点落在本模块的职责和契约上，不由调用方反向定义。
   - 不把方法清单、参数表、代码示例、配置字段清单或逐调用生命周期写入概览，除非它们是模块契约且缺失会导致错误使用。
   - 区分请求受理、存储写入、workflow 完成和主机实际生效，不跨层推导成功。
   - 每项技术细节都要解释当前层的行为、限制或决策；不能自行变成上层业务叙事。

3. **Answer And Subquestions**
   - 开头直接回答原始问题，再提供原因、规则和边界。
   - 每节只回答一个明确子问题；标题无需强制写成问句。
   - 按读者理解关系组织内容，不按源码目录或函数调用顺序展开。
   - 模型来自当前业务；`Permission -> Scope -> Intersection -> Endpoint Policy` 仅是权限场景示例。

4. **Representation And Evidence**
   - 按下表选择表达方式；简单规则直接写文字，不为凑结构强制配图。
   - 图表与正文共享事实来源；检查入口、条件、关键分支和结果是否一致。
   - 重要结论保留对应源码位置、契约或验证结果；区分已实现、已启用和已验证的效果。
   - 没有测量结果，不宣称性能提升；未核实的事实按读者边界规则处理。

5. **Clarity And Terminology**
   - 删除无信息密度句子（例如“本文将介绍…”、“不展开细节…”）。
   - 一句表达一个事实，同一事实不在图表和正文中无增量重复。
   - 同一业务概念全篇同名，以项目术语为准，不为增加 English technical terms 翻译普通词。
   - 精简不能删除成立条件、异常、兼容性限制或读者必需的操作。
   - 不以固定字数、章节数或渲染成功替代内容验收。

6. **Overview Scope**
   - 代码层 README 默认从一句话定位开始，随后说明职责边界和稳定前提；没有必要的逻辑分支、状态或结果语义时，不增加流程图、状态图或详细章节。
   - 上层业务如何使用本模块，由上层 README 向下引用说明；下层 README 不反向链接。
   - “高信息密度”不等于信息越多越好。删除不影响使用判断的背景、演进方向、重复解释和实现过程。

## Representation Guide

| 信息关系           | 推荐表达           | 检查重点                     |
| ------------------ | ------------------ | ---------------------------- |
| 条件与决策分支     | 流程图或规则表     | 入口、条件、结果、例外       |
| 多个参与者的交互   | 时序图             | 谁调用谁、何时返回、完成边界 |
| 生命周期           | 状态图或状态转换表 | 触发条件、终态、失败路径     |
| 多维差异或可用边界 | 表格               | 比较维度一致，条件不丢失     |
| 简单规则或结论     | 短段落或列表       | 直接回答，不强行建模         |

文档中的图沿用项目 Mermaid 惯例；其他呈现工具只负责渲染，不改变内容标准。

## Output Contract

README 通常从模块目标进入，补充职责边界、稳定前提、必要规则、结果和深入链接。代码层 README 优先保持概览，深入链接只指向本目录或下层依赖；只有本模块拥有对应契约时，才展开分支、状态、例外或使用入口。逻辑说明围绕当前问题组织，无需为不相关内容保留空章节。

读者正文应能独立回答问题，并包含必要的来源与边界。文件索引仅用于进一步定位，不作为正文主线。交付时将作者核验事项与读者正文分开。

## Business Anchor Example

解释可选 ORM batching 时，先说明默认直接写入、显式启用范围、每个调用何时返回和取消边界。队列或 `singleflight` 只用于解释这些行为。不得把 ORM 写入完成写成整个 operation 完成，也不得把可选能力写成业务 DAO 已启用或性能收益已验证。

权限场景仍需分别解释“无授权实例”和“请求无交集”，依据实际 endpoint 契约说明各自返回策略；不能合并为一个笼统的“无权限”。

## Common Mistakes

| 问题                         | 修正                                                       |
| ---------------------------- | ---------------------------------------------------------- |
| 技术机制取代原始问题         | 说明该细节解释哪个业务结果，否则删去                       |
| 代码层 README 向上依赖       | 删除调用方场景及其链接，回到本模块职责、稳定前提和能力边界 |
| 为了“逻辑完整”堆入 API 细节  | 删除方法、参数和调用过程，只保留影响模块使用判断的契约     |
| 所有模块套权限四层模型       | 从当前业务抽取模型                                         |
| 简单规则也必须画图           | 用文字或列表直接回答                                       |
| 图表为连通而补出未证实的路径 | 对照事实逐条检查连线、条件与返回语义                       |
| 缩短篇幅时删掉例外           | 保留影响读者判断的条件和失败结果                           |

## Quick Review Checklist

- [ ] 回答了吗：开头回答原始问题，读者知道如何判断或操作
- [ ] 解释了吗：各节回答子问题，说明决定结果的条件与关系
- [ ] 失真了吗：证据支持结论，图文一致，边界和业务层级未丢失
- [ ] 跑题了吗：每段都服务原始任务，技术细节未取代业务主线
- [ ] 依赖方向：代码层 README 自洽，只向下依赖；无上层调用方场景、结果或链接
- [ ] 表达合适：术语一致，无空话和无增量重复，未强制配图、API 细节或领域模型

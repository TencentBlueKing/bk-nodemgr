# bk-nodemgr Code README

## Overview

本 skill 用于编写和重构 bk-nodemgr 代码目录中的 README，包括 `pkg/**`、`internal/**`、`tools/**` 等模块。

目标是帮助读者理解该代码模块的职责、边界和使用前提；README 的深度由模块拥有的契约和读者任务决定。

## When to Use

用于代码目录 README 的新建、重写或结构调整，例如：

- 用户要求编写或重构 `pkg/**`、`internal/**`、`tools/**` 等代码目录内的 README
- 用户要求精简包级说明或澄清模块的职责、非职责与稳定前提

不适用：

- `docs/**` 下的 README 或一般逻辑文档
- API reference、changelog、PR 描述、Issue、代码审查
- 不涉及逻辑或结构的一两句文案修改

需要选择文档位置时，先用 `bk-nodemgr-agent-information-architecture`。需要处理读者正文与作者核验事项时，配合 `bk-nodemgr-audience-boundary`。本 skill 不替代专用文档格式。

## Mandatory Workflow

1. **Policy And Module Context**
   - 先读取适用于目标目录的 `AGENTS.md`，再读模块源码、契约和至少一个相邻或同职责的 README。
   - 明确读者、阅读目标，以及该 README 所属模块的职责。
   - 内容按模块拥有的契约和读者任务取舍，不沿源码目录或调用顺序罗列。

2. **Architecture Ownership**
   - 只陈述有证据支持、属于本模块的职责、契约、限制和前提；不要把调用方的策略或业务结果写成本模块行为。
   - 遇到职责归属、依赖方向或跨层协作不清楚时，先调用 `bk-nodemgr-architecture-judgment` 收集架构判断；不要在本 skill 中自行发明目录层级规则。
   - 架构边界明确时，无需为普通单模块 README 强行增加架构审查流程。

3. **Choose Scope And Depth**
   - 通常从模块定位、职责/非职责和稳定前提出发，作为默认建议而非内容上限。
   - 当本模块拥有读者必须理解的分支、状态、结果语义或使用契约时，再按需展开，并说明这些内容如何影响对本模块的使用或判断。
   - 不默认写逐函数 API、实现过程、调用方 workflow 或跨模块业务结果；仅当它们本身构成本模块契约且省略会导致误用时才纳入。
   - 区分本模块可保证的结果和调用方、workflow、外部系统才能判定的最终结果。

4. **Explain And Verify**
   - 开头直接说明模块是什么、解决什么问题；章节分别回答读者的具体问题。
   - 简单规则用短段落或列表；只有存在分支、交互、生命周期或多维边界时才考虑图表。
   - 图表和正文基于同一事实来源；检查入口、条件、关键分支与结果是否一致。
   - 重要结论应能追溯到源码、契约或实际验证；没有测量结果，不宣称性能收益。
   - 使用项目已有术语；精简时保留成立条件、异常、兼容性限制及读者必须执行的操作。

## Representation Guide

| 信息关系                 | 推荐表达           | 检查重点                   |
| ------------------------ | ------------------ | -------------------------- |
| 条件与决策分支           | 流程图或规则表     | 入口、条件、结果、例外     |
| 有契约意义的多方交互     | 时序图             | 参与者、返回时机、完成边界 |
| 本模块拥有的生命周期契约 | 状态图或状态转换表 | 触发条件、终态、失败路径   |
| 多维差异或可用边界       | 表格               | 比较维度一致，条件不丢失   |
| 简单规则或结论           | 短段落或列表       | 直接回答，不强行建模       |

图表只描述本模块拥有或可保证的契约；跨模块图示需能从架构关系和事实证据中核实。沿用项目已有的 Mermaid 惯例。

## Output Contract

README 通常从模块定位进入，说明职责、非职责和稳定前提；按模块契约与读者任务决定是否增加规则、分支、状态、结果或操作细节。深入链接应帮助读者理解本模块契约，不得将调用方业务描述成模块行为。

读者正文应独立回答目标问题并保留必要边界。将作者核验事项与读者正文分开。

## Common Mistakes

| 问题                               | 修正                                             |
| ---------------------------------- | ------------------------------------------------ |
| 调用方策略被写成模块行为           | 核实职责归属；边界不清时交由架构判断 Skill 处理  |
| 为了“逻辑完整”堆入 API 或实现细节  | 只保留属于本模块契约且影响读者判断的内容         |
| 不同模块被强行套用相同业务模型     | 从目标模块的契约和读者任务组织内容               |
| 简单规则也必须画图                 | 用文字或列表直接回答                             |
| 图表为连通而补出未经架构核实的路径 | 核对模块关系、条件与结果，不能确定时先做架构判断 |
| 缩短篇幅时删掉例外                 | 保留影响读者判断的条件和失败结果                 |

## Quick Review Checklist

- [ ] 回答了吗：开头回答原始问题，读者知道如何判断或操作
- [ ] 解释了吗：各节回答子问题，说明决定结果的条件与关系
- [ ] 失真了吗：证据支持结论，图文一致，边界和业务层级未丢失
- [ ] 跑题了吗：每段都服务原始任务，技术细节未取代业务主线
- [ ] 模块边界：内容属于目标模块；调用方策略未被写成本模块保证，架构疑问已交由架构判断 Skill
- [ ] 表达合适：术语一致，无空话和无增量重复，未强制配图、API 细节或领域模型

## [Version: v3.0.1-alpha.101] - 2026-10-21

Full Changelog: [v3.0.1-alpha.100...v3.0.1-alpha.101](https://github.com/TencentBlueKing/bk-nodemgr/compare/v3.0.1-alpha.100...v3.0.1-alpha.101)

**Release scope**

- Backend/Control Plane: Adds Windows firewall deployment configuration, legacy V2 plugin conflict checks, and Node workflow concurrency limits and retry backoff.
- Plugin/Package: V3 plugin packages can declare an installation disk IO limit; package upload and publish operations gain server-side permission prechecks.
- Installer/Deployment: Windows firewall rules can be applied before installation; the Installer supports disk IO limiting while processing packages; IAM/API Gateway sync Jobs in KMS deployments resolve application credentials from encrypted configuration.
- Topology: Improves topology operation record filters and operator information.

**New features**

- V3 plugin `project.yaml` accepts the optional `installDiskIoLimit` setting (MB/s) to limit logical read/write speed while processing tgz packages during installation or upgrade. If unset or set to `0`, no limit is applied; V2 plugin packages ignore this setting.
- The plugin install API can enable a legacy V2 plugin running-state check. For a V3 plugin package that declares a legacy conflict, installation is blocked when a same-name V2 plugin is running on the target host. Stop the conflicting V2 plugin before installation when this check is enabled.
- Windows Agent deployment can configure the `gse` and `nodemgr` firewall features and allowed CIDRs. An empty feature list leaves firewall rules unmanaged; individual IPv4 and IPv6 addresses must use `/32` and `/128` CIDR notation, respectively.
- Node install, upgrade, reconfigure, restart, uninstall, and Proxy Unit assignment workflows have independent Global Settings named `oper_node_<operation>_max_concurrency_num`, where operation is `install`, `upgrade`, `reconfig`, `restart`, `uninstall`, or `assign_proxy_unit`. Each defaults to `200` and must be a positive integer. Limits apply per trigger, not to aggregate concurrency across workflows.
- adminclient adds `bkapp code` and `bkapp secret` commands to resolve application credentials from the KMS global envelope for Helm IAM V3/V4 and API Gateway sync Jobs. Non-KMS deployments retain their existing credential configuration.

**Improvements**

- Topology operation records can be filtered by cloud area, control unit, operation type, and operator. Operator display and pagination after filtering are also improved.
- Node Action retries use exponential backoff with random jitter instead of fixed delays. Timeouts and retry counts remain unchanged; subsequent retries and final failure reporting for some actions may take longer.
- Batches ORM and workflow operation-instance field writes and coalesces concurrent reads of the same global setting to reduce duplicate storage requests.

**Bug fixes**

- Fixes loss of the underlying error when Windows SSH installation fails, an incorrect error label for download server configuration, an incorrect deploy policy scope type error message, and incorrect error handling for invalid cloud area IDs.
- Fixes inaccurate operator information in topology operation records.
- Package upload and publish endpoints check `package_type_upload` permission for the corresponding package type before parsing requests or performing file operations, and stop when authorization fails.
- Fixes Agent/Proxy operations-field updates being rejected when an existing host has a different node role. Host existence checks and business-operation authorization remain in place.
- Fixes invalid tracing exporter types being reported as missing types, preserving the underlying validation error for startup configuration diagnosis.

**Agent / Plugin / Package compatibility**

- `installDiskIoLimit` is optional. If unset or set to `0`, package processing remains unlimited; legacy V2 plugin packages do not use this setting.
- The Installer executing an install or upgrade script needs `--diskio-limit` support only when a V3 plugin package sets a positive `installDiskIoLimit` and the generated script includes that flag. No Installer upgrade is required for this setting otherwise.
- Omitting `firewall` from a control unit inherits deployment defaults; explicitly setting an empty object `{}` disables firewall setup. When the effective configuration enables setup, rules are applied for the selected features and allowed CIDRs.
- Node concurrency settings are fixed when a trigger is created. Changes affect only new triggers; retries reuse the original trigger.
- Package upload and publish request and successful-response fields remain unchanged. Requests previously not blocked by permission checks must now pass authorization for the corresponding package type.

**Component dependencies and upgrade prerequisites**

- On hosts where the enabled V2 plugin conflict check finds a conflict, stop the running same-name legacy V2 plugin before installation.
- When using `installDiskIoLimit`, the deployed Installer must support `--diskio-limit`. The value must be a non-negative number of MB/s; negative or non-numeric values fail plugin package import validation.
- Windows firewall rules are applied by the Installer before installation. Verify that configured features and CIDRs are appropriate; firewall rules are not managed when no features are configured.
- Before upgrading, ensure package upload and publish operators have `package_type_upload` permission for the corresponding `package_type` resource. These operations stop if the backend authorization service is unavailable.
- For KMS deployments, upgrade the chart and related images together so sync Job images include `bk-nodemgr-adminclient bkapp`. KMS-enabled sync Jobs require `backend.enabled: true`, access to the KMS global envelope, and the private key injected through `BK_NODEMGR_KMS_PRIVATE_KEY_GLOBAL`; Helm obtains this value from the global KMS Secret's `privateKey`.

## [Version: v3.0.1-alpha.115] - 2026-11-18

Full Changelog: [v3.0.1-alpha.114...v3.0.1-alpha.115](https://github.com/TencentBlueKing/bk-nodemgr/compare/v3.0.1-alpha.114...v3.0.1-alpha.115)

> Important notes

- Username compatibility is no longer determined by tenant mode. When upgrading Node Management on BlueKing platform 7.2, set both `backend.config.userManager.useLegacyUsername=true` and `application.config.userManager.useLegacyUsername=true`. On BlueKing platform 7.3, keep the default `false` in both single-tenant and multi-tenant deployments. `true` is supported only in single-tenant mode.
- The NodeMan offline migration tool applies only when upgrading BlueKing platform 7.2 to 7.3, to backfill NodeMan main plugin processes and main configs into NodeMgr. It does not automatically migrate Agents or plugin packages. Importing does not delete existing data, but overwrites matching process and config records.

**Release scope**

- Backend/Control Plane: User identity resolution and legacy username compatibility.
- Application/Frontend: Application user identity resolution and legacy username compatibility.
- Installer/Deployment: Username compatibility configuration and an offline migration tool for NodeMan main plugin processes.

**New features**

- Adds an offline export tool for NodeMan main plugin processes. It generates files grouped by tenant, business, and plugin for import with `mongosh`, allowing selected groups of legacy V2 plugin process records and main configs to be backfilled.

**Bug fixes**

- Fixes single-tenant mode treating `login_name` directly as `bk_username`. By default, user management is queried for the current tenant's virtual-user mapping, supporting single-tenant deployments on BlueKing platform 7.3. BlueKing platform 7.2 deployments can explicitly enable legacy username compatibility.

**Agent / Plugin / Package compatibility**

- This release does not change Agent, Plugin, or Package formats. Existing business API paths and request/response structures are unchanged.
- The migration tool only backfills main plugin process and main config records; it does not replace Agent upgrades or plugin package migration.

**Component dependencies and upgrade prerequisites**

- When upgrading BlueKing platform 7.2 to 7.3, switch `userManager.useLegacyUsername` to `false` in both Backend and Application. Grant the Node Management application access to user management's `GET /open/tenant/virtual-users/-/lookup/`, and correctly configure `userManager.endpoints`, application credentials, and the request tenant identity for both services. Single-tenant deployments use tenant `default`. Query failures, permission errors, or missing user mappings return errors without falling back to `bk_username = login_name`.
- `userManager.useLegacyUsername` is independent of the existing `application.config.bkSaaS.bkLogin.useLegacyAPI` and does not replace login API compatibility configuration. Keep both services' settings in sync in Helm/Helmfile. Docker Compose templates also default to `false`; change both to `true` before deploying on BlueKing platform 7.2.
- Exporting requires the original NodeMan Django environment connected to its original database. Transfer the exported files to NodeMgr, confirm the target database, and import with `mongosh`. Import uses `upsert` to insert or update only the records in the files, without deleting other existing data.

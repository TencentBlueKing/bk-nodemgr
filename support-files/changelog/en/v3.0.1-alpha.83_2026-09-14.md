## [Version: v3.0.1-alpha.83] - 2026-09-14

Full Changelog: [v3.0.1-alpha.82...v3.0.1-alpha.83](https://github.com/TencentBlueKing/bk-nodemgr/compare/v3.0.1-alpha.82...v3.0.1-alpha.83)

> Important notice

- IAM v4 model initialization and runtime authorization remain disabled by default. Upgrading neither switches from IAM v3 to v4 automatically nor migrates existing grants. Enabling model initialization still does not migrate user group grants or resource scopes; validate authorization and permission application flows after registering the model.
- Backend package queries, state management, and event queries now use File Service. Upgrade or roll back Backend and File Service together to avoid new Backend instances calling APIs unavailable in older File Service versions.
- The Helm package initialization Job now passes `--set-as-default` by default, enabling selected Agent, Proxy, and Plugin packages and changing their default versions. Check input packages and processing order before execution; selection does not choose the latest semantic version.

**Release scope**

- Agent / Proxy: Initial package enablement and default version selection.
- Plugin: Plugin lists, process details, installation version selection, and Relay working directories.
- Package: File Service release management, package event queries, and initialization request timeouts.
- Backend/Control Plane: IAM v4 callbacks and permission models, task history permissions, task details, and log pages.
- Installer/Deployment: IAM v4 Helm initialization and configuration, and default package initialization.

**New features**

- IAM v4 initialization adds the local business resource `biz`, 32 actions, and four roles, with limited updates and `--dry-run` prechecks.
- IAM v4 resource callbacks support list and detail queries for businesses, network areas, network units, package types, and packages, with API Gateway registration, tenant propagation, and a dedicated v4 response protocol.
- File Service adds release query and management APIs and package event queries, centralizing enablement and default version management for Agent, Proxy, and Plugin packages, and release metadata deletion across package types.
- The initialization script can enable published packages and set them as defaults per platform. Manual runs opt in with `--set-as-default`; certificates and tool packages still only go through upload and publish.
- A new per-tenant scheduled task queries enabled plugin releases every minute and creates missing default plugin records. It neither changes default package versions nor deploys plugins to hosts.

**Improvements**

- Initialization request timeouts for uploads, publishing, and state operations increase to 30 minutes throughout, allowing more time for large packages and slower publishing operations.
- Relay working directories now use `/tmp/bknm/{deploy_env}/relay`, or `c:/tmp/bknm/{deploy_env}/relay` on Windows, when no explicit directory is configured, reducing shared-directory conflicts between environments.

**Bug fixes**

- Agent, Proxy, and Plugin task history, operation instance, and log queries use their respective history-view permissions instead of incorrectly requiring resource-view or operation permissions.
- Fixed incomplete cross-page batch retry, termination, and IP copying in task details. Log pages use server-side pagination and filtering; node task navigation carries the target IP filter.
- Fixed plugin lists not refreshing after switching businesses, missing host information from the second process page onward, and installation defaults being affected by other plugins' versions. Upgrade tables allow removing extra host rows.
- Fixed IAM v4 Helm settings not being emitted into Backend configuration, and distinguished callback credential errors from token service failures.
- Separated disabled IAM behavior from authorization bypass: direct IAM calls and callback authentication for a disabled version return errors instead of allowing access. Backend skips business authorization only when both IAM v3 and v4 runtime authorization are disabled.
- Fixed topology page creation permission checks: network area creation uses a resource-free check, while network unit creation is checked against its parent network area. Permission application flows and IAM v3/v4 permission models remain unchanged.
- Corrected the initialization script's Proxy/Server publish endpoint to `/api/v3/publish/release/proxy`.

**Agent / Plugin / Package compatibility**

- This version does not change Agent / Proxy, Plugin, or Package package formats. The tenant-isolated storage and download path requirements introduced in alpha.82 still apply.
- Explicit Relay `WorkspaceFileGroupFullPath` settings remain unchanged and do not gain automatic environment isolation. Check shared paths before redeployment; an unset deployment environment defaults to `dev`.
- IAM v4 callbacks use string-valued `method`, top-level `requires`, and dedicated `data` / `error` responses rather than the IAM v3 callback protocol. Update custom callers accordingly.

**Component dependencies and upgrade prerequisites**

- Enable IAM v4 initialization with `iamV4.enabled` and runtime authorization separately with `backend.config.iamV4.enable`. Disable v3 runtime authorization before enabling v4. Configure the `bkiam` gateway and application credentials under `backend.config.iamV4`, and include the application code in `iamV4.system.clients`.
- Configure a reachable `iamV4.provider.host` and the `/api/v3/iam/v4/resource` callback path. Callbacks use Basic Auth with `bk_iam` and the system token; multi-tenant requests must carry `X-Bk-Tenant-Id`.
- The IAM v4 Helm Job runs after installation and upgrades. It initializes only `default` in single-tenant mode or `system` in multi-tenant mode, without iterating tenants. Use a Backend image containing the v4 migration tools and run `--dry-run` against the target tenant before execution.
- Conflicts in IAM model ancestor chains, action resource bindings, role member removal, or dimension changes stop migration. Job failures block the Helm release; model writes are not rolled back automatically. Check remote state before rerunning or rolling back. Adding actions to existing roles may grant users new permissions within existing resource scopes; confirm the impact first.
- Default package selection follows processing order: Agent uses the last input package, and Proxy and Server share a group. Plugins are grouped by input type and plugin name and use the last successfully uploaded package. A failed target publish does not fall back to an earlier package, older packages do not fill missing platforms, and partial success is not rolled back. Check per-platform defaults and the failure summary afterward, and allow sufficient time in outer waits such as Helm.
- Verify Backend-to-File Service connectivity, authentication, and tenant settings, then validate package queries, enablement, default versions, and event records. Multi-tenant package initialization requires File JWT authentication with a matching key.
- Default plugin record creation requires Backend access to enabled plugin releases for the corresponding tenant. Before rolling back this feature, disable or delete its scheduled workflow for each tenant.
- **To be confirmed**: Integration results for the target IAM v4 deployment version, and the migration and rollback plan for existing IAM v3 grants. Retain the current authorization configuration until these are confirmed.

**Known issues**

- Deploy policy `ensure_absent` is only saved by updates and returned in lists, defaulting to `false`. The executor does not implement reverse deletion or uninstallation. Setting it to `true` still runs existing execution logic and must not be used to clean up plugins or configurations.

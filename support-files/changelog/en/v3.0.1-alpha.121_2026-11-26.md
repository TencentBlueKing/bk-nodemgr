## [Version: v3.0.1-alpha.121] - 2026-11-26

Full Changelog: [v3.0.1-alpha.120...v3.0.1-alpha.121](https://github.com/TencentBlueKing/bk-nodemgr/compare/v3.0.1-alpha.120...v3.0.1-alpha.121)

> Important notes

- The built-in topology query (`topo`) and execution diagnostics (`execution`) MCP servers become public, while system diagnostics (`system-diagnosis`) remains non-public. All three support public client OAuth2 and personal client tokens. Calls still require the corresponding user authentication and resource permissions. Review the target stage's visibility and authorization policies before synchronizing the upgrade.
- The Backend Jinja2 renderer now reuses a local service and requires an available loopback listening port in the configured range, `28150–28159` by default. These ports do not need to be exposed externally.

**Release scope**

- Backend/Control Plane: Plugin requirement file management, plugin Process requirement records, Jinja2 configuration rendering, and default direct Network Unit Access Points.
- Application/Frontend: Built-in Wiki reader, platform management navigation and access control.
- Installer/Deployment: MCP product catalog and authentication settings, Helmfile computed values export, and Jinja2 and Network Unit configuration.

**New features**

- Backend provides APIs for creating plugin requirement files, replacing content, updating applicability, retrieving metadata, listing with pagination, and downloading content. File maintains independent file records whose applicability can be limited by operating system, CPU architecture, and Plugin Package version.
- Plugin Processes support storing the record ID, target path, target file name, and MD5 of actual requirement files. Routine Process updates preserve these records.
- `system-diagnosis` MCP adds a read-only system configuration query. It returns the whitelisted business configuration loaded at startup by the responding Backend instance, excluding credentials, connection endpoints, and internal observability settings. It does not imply consistent configuration across all replicas.
- Adds a built-in Chinese and English Wiki reader with Markdown rendering, a table of contents, and internal document links, reusing the existing Web login flow.
- Adds platform management navigation that displays menus and verifies page access according to `platform_manage` authorization on `system_config`, `scheduler_workflow`, and `global_settings`. All three pages are placeholders and do not provide management operations yet.
- Automatic creation of the default direct Network Unit can also create downstream Access Points for Proxies from other Network Units to connect to it.
- Supports a separate Redis Sentinel authentication password for Backend, File, workflows, and Adminclient connections.
- `execution` MCP adds a read-only query for historical Agent / Proxy installation parameters, without returning authentication credentials or creating or retrying installations. Historical records are not complete request snapshots; callers must inspect `missing_fields` and `unavailable_operation_ids` rather than treating missing values as previous choices.

**Improvements**

- Simplifies the Agent Management and Proxy Management menu and page titles to Agent and Proxy.
- Jinja2 configuration rendering for V3 plugins and legacy V2 plugins reuses an embedded service, supports concurrent requests, reduces repeated renderer startup overhead, and adds tracing and request metrics.
- Helmfile `render-values` exports the computed values, including Chart and enabled subchart defaults, template-generated values, and user overrides, with the same precedence as deployment. It neither modifies the original Chart nor deploys to the cluster.

**Bug fixes**

- Fixes the Helmfile example configuration forcing Jinja2 trace sampling off. When the Gateway is enabled and no sampling rate is explicitly configured, Jinja2 enables sampling alongside other Backend components.

**Agent / Plugin / Package compatibility**

- This release does not change Agent, Plugin, or Package formats.
- Requirement file records, Plugin requirement declarations, and actual Process requirement state are independent objects. This release provides file management APIs and storage for Process requirement records, but does not provide Plugin requirement declaration management, automatic distribution, or application workflows. Backend does not expose a requirement file transfer API.

**Component dependencies and upgrade prerequisites**

- To use the plugin requirement file management APIs, upgrade Backend and File together. Creation and updates require `plugin_operate`; queries and downloads require `plugin_view`, with checks against the current tenant and plugin visibility scope. These six APIs are included in the API Gateway resource catalog and require synchronization and publication before gateway access. The resources are private with self-service permission applications disabled; callers must pass application authentication and obtain gateway resource authorization.
- To use the updated built-in MCP servers, upgrade the Chart and apigw-sync image together, publish the corresponding user-state gateway resources, and synchronize the MCP definitions. Built-in mode remains disabled by default; enabling it requires `apigwSync.mcp.enabled: true` and `spec_version: 2`. Explicit stage catalogs still replace the built-in catalog entirely and do not automatically receive new tools. The user-state system configuration gateway resource now explicitly requires user authentication, along with `system_access` and `platform_manage` on `platform_resource/system_config`. System diagnostics remains intended for authorized internal maintainers; its global configuration query may return sensitive settings.
- To use the built-in Wiki reader, set `backend.config.wiki.mode: application`, set `backend.config.wiki.application.prefixURL` to a user-accessible URL prefix ending in `/#/wiki/`, and enable `application.config.wiki.enabled`. The ingress proxy must preserve any deployment subpath and forward raw document requests to Application's `/wiki/`. The previous `/wiki/` prefix still serves raw Markdown directly. Raw documents remain anonymous and read-only and must not contain sensitive information.
- `backend.config.networkUnit.defaultDirectUnit.accessPoints` defaults to an empty list. Access Points are created through scheduled synchronization only when no direct Network Unit exists in the default Network Area (ID 0). Existing units and Access Points are not updated automatically. When automatic creation is enabled, the unit name must be non-empty, and each Access Point requires a name and at least one `IP:port` address for each cluster, file, and data channel; otherwise Backend fails to start. Downstream addresses must use Proxy access ports rather than directly reusing the upstream addresses for Agents in the direct unit.
- The Jinja2 port range can be adjusted through `backend.config.jinja2x.portRange`. Ports must be within 1–65535, and the end port must not be less than the start port. The Chart defaults `traceSampleRate` to `0`. With Helmfile and the Gateway enabled, an unspecified sampling rate is set to `1`; explicit settings take precedence. If the embedded service exits, the next render recreates it automatically; the failed request itself is not retried automatically.
- When Redis Sentinel requires authentication, set `externalRedis.sentinelPassword` for Backend and File; keep the data node password in `externalRedis.password`. KMS mode uses `redis.default.sentinel_password` from the global envelope, overriding `redis.sentinelPassword` in the configuration file.
- Helmfile `render-values` skips dependency downloads by default, so the Chart must already contain the required dependencies. Remote Charts require a configured, accessible Helm repository. Exported computed values may contain credentials and should not be shared directly.

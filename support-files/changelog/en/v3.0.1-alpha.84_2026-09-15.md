## [Version: v3.0.1-alpha.84] - 2026-09-15

Full Changelog: [v3.0.1-alpha.83...v3.0.1-alpha.84](https://github.com/TencentBlueKing/bk-nodemgr/compare/v3.0.1-alpha.83...v3.0.1-alpha.84)

> Important notice

- IAM v4 roles are further separated: Agent / Proxy roles no longer include plugin permissions, and network area creation requires a dedicated grant. Model updates do not transfer existing grants to new roles. Check affected users' roles and resource scopes before upgrading.
- The deploy policy `Execute` response now returns the parent `workflow_id` instead of `trigger_id`, without an alias for the old field. Update response parsing and use `WorkflowList` to query executions. The previously documented `WorkflowResult` contract has been removed; that endpoint is not provided.

**Release scope**

- Agent / Proxy / Plugin: Task history authorization and deploy policy execution records.
- Package: Scheduled shared release synchronization, shared and synced states, package uploads, and list interactions.
- Backend/Control Plane: IAM v4 roles and creator grants, topology history permissions, deploy policy execution queries, status monitoring, and etcd service discovery.
- Installer/Deployment: IAM v4 model update tools and Alpine container dependencies.

**New features**

- IAM v4 provides separate management or read-only roles for Agent, Proxy, Plugin, config policies, topology, and packages, and separates network area creation from management. Role action membership supports in-place additions, removals, and resource-dimension changes without deleting and recreating roles.
- Network area and network unit creators receive management permissions for the newly created resource. IAM v4 grants last 365 days without automatic renewal.
- Package publishing accepts `is_shared`; lists return and support filtering by `is_shared` / `is_synced`. Multi-tenant pages display synced sources, and non-certificate uploads in the `system` tenant offer sharing enabled by default.
- Non-`system` tenants synchronize shared releases from the `system` tenant every 10 minutes, covering Agent, Proxy, Plugin, certificates, and tool packages. Synchronized copies are marked `is_synced`.
- Deploy policy executions persist tenant-scoped policy workflows and associated Node / Plugin child workflows for manual runs, scheduled runs, and related policies. The new `WorkflowList` supports pagination, counts, and filtering by workflow, policy, status, operator, and operation time. Background monitoring synchronizes parent dispatch status and finish time.

**Improvements**

- Multi-tenant virtual user lookups are cached locally by tenant and login name for one minute, reducing repeated requests to User Management.
- Alpine service images include `bash` for operational scripts that require it.

**Bug fixes**

- Node workflow history permissions are checked against stored businesses and node roles rather than request filters alone. Corrected list and count results when query filters do not intersect the authorized scope.
- Network area history queries include child events under the area's history permission, fixing unnecessary child-resource permission requirements and empty authorization intersections.
- Fixed missing resource names and empty permission application dialogs, stale authorization responses overwriting newer page state, and permission-denied views remaining after grants change.
- Plugin package lists filter by view rather than management permissions and do not send unfiltered queries before permissions load or when no plugins are viewable. Fixed plugin upload type display and unnecessary close confirmation before a file is uploaded.
- Fixed panics during error-code mapping when package version operations are denied permission, while preserving permission application details.
- Fixed repeated writes in the etcd service discovery fallback, preventing unchanged registrations from continuously increasing MVCC revisions and storage usage.

**Agent / Plugin / Package compatibility**

- This version does not change Agent / Proxy, Plugin, or Package formats. Tenant-isolated storage, download paths, and coordinated component requirements from alpha.82/83 still apply.
- Shared release synchronization preserves tenant-owned packages and skips synchronized copies whose MD5 has not changed. Disabling sharing on a source release does not automatically delete existing copies. Omitting `is_shared` from a publish API request defaults it to `false`.

**Component dependencies and upgrade prerequisites**

- Run `--dry-run` before updating IAM v4 models and review removed role actions and grants for new roles. Updates stop if IAM rejects member removal, and completed changes are not rolled back automatically. Check remote models and grants before rerunning or rolling back. Deploy policy actions are removed from the templates, but registered actions and the old `policy_manager` role are not automatically deleted.
- IAM v4 initialization and runtime authorization remain independently enabled. Upgrades do not switch IAM versions or migrate IAM v3 grants automatically. Failed creator grants do not undo resource creation; check logs and grant permissions separately.
- Upgrade Application, Backend, and File Service together, synchronize API Gateway definitions and `Execute` callers, and validate package states, permissions, and `POST /api/v3/deploy_policy/workflow/list`. Rollback must also restore caller response parsing; do not mix old and new execution IDs.
- Backend requires access to create, read, and write `deploypolicy_workflow_{tenantID}` collections and create their unique indexes, and to read parent operations for status synchronization. Verify background status updates after upgrading. Legacy records without status are backfilled automatically; unfinished records with a missing operation become `failed` after a one-minute grace period.
- Shared release synchronization requires Backend scheduling and the matching File Service. Review the `system` tenant's shared releases before upgrading, then check synchronization tasks and copies in non-`system` tenants.
- **To be confirmed**: Role changes, replacement grants, and rollback procedures in the target IAM v4 environment.

**Known issues**

- Parent `success` means dispatch succeeded, not that child deployments completed. Status updates are asynchronous. Query child results through existing Node / Plugin workflow APIs with their respective permissions; parent visibility does not grant child access.
- Dispatch actions do not retry automatically, and no deploy-policy workflow retry or terminate API is provided. Each new `Execute` creates another execution. Failed dispatch does not terminate already launched children; callers must check child results before chaining policies.

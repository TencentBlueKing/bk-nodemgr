## [Version: v3.0.1-alpha.81] - 2026-09-07

Full Changelog: [v3.0.1-alpha.80...v3.0.1-alpha.81](https://github.com/TencentBlueKing/bk-nodemgr/compare/v3.0.1-alpha.80...v3.0.1-alpha.81)

> Important notice

- IAM v4 is disabled by default. Upgrading does not automatically switch existing IAM v3 authorization. Before enabling IAM v4, configure its permission model and grants, and validate authorization checks, resource scopes, and permission application flows.

**Release scope**

- Plugin: Adjusted process startup timeouts and fixed the stop flow when taking over legacy plugins.
- Backend/Control Plane: Added optional IAM v4 runtime authorization.
- Installer/Deployment: Added IAM v4 system migration tools; Helm, image versions, and API Gateway release metadata are aligned to v3.0.1-alpha.81.

**New features**

- Added IAM v4 runtime support for single and batch authorization, authorized resource scope queries, permission application links, and a dedicated resource callback, retaining the existing Action/Resource permission model.
- Added IAM v4 system template rendering and migration tools with prechecks and system registration/update support.

**Improvements**

- Increased the process startup step timeout in Plugin v2/v3 workflows from 1 minute to 5 minutes, allowing more time for slower-starting plugins.

**Bug fixes**

- Fixed legacy plugin takeover skipping the stop step when Node Manager has no process record. Plugins are now stopped according to their actual running status in GSE.

**Agent / Plugin / Package compatibility**

- This version does not change Agent / Proxy, Plugin, or Package package formats.
- Legacy plugin takeover uses the running version's plugin package to build stop parameters, falling back to the user-specified version if that package cannot be retrieved. Ensure the required package is available and verify that the fallback version's stop command and configuration paths match the running plugin.

**Component dependencies and upgrade prerequisites**

- Enabling IAM v4 requires an IAM v4 gateway with a registered permission model and grants. Configure the gateway connection, `systemID`, and `callbackPath` under Backend `iamV4`, and ensure IAM can reach the `/api/v3/iam/v4/resource` callback.
- `iamV3.enable` and `iamV4.enable` cannot both be `true`. Disable IAM v3 when enabling IAM v4; environments that are not switching should keep `iamV4.enable=false`.
- The IAM v4 migration tool only supports `upsert_system`; it does not migrate resource types, actions, roles, or grants. Run `--dry-run` before execution. Interrupted execution does not roll back completed operations; check remote state before rerunning. Complete permission configuration and migration validation separately before switching; enabling the configuration alone does not perform a migration.

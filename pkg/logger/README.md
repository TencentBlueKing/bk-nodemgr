# logger

## 设计意图
提供全局的日志功能，包括输出到文件和标准输出。

## 功能边界
1. 此包负责：
    - 日志文件管理（滚动、分级、软链）
    - 日志参数格式化（带error、带参数、带时间区间）
2. 此包不负责：
    - 处理参数逻辑
    - 定制第三方日志接口

## 设计考量
采用全局单例的模式，目的为：
- 调用便捷，全局统一
- 文件层级固定，runtime.Caller准确
- 区分业务（Business）和系统（System）日志

## 使用限制
1. 当需要对接第三方库的日志时，应该在第三方库的引用处实现其日志接口，并采用logger打印
2. 当打印错误时，应统一使用WithErr(err)
3. 当打印参数时，应尽量使用With("a", a, "b", b)的形式，也可以是With("a", a).With("b", b)，必要情况下也允许在日志(Debug/Info/Warn/Error)里直接格式化。
4. 日志内容应该尽量为一个完整的英文句子，避免被参数隔开（整个句子可以过滤到），避免使用无效信息，如"please", "maybe", "!!!"等
5. 日志级别的选择：
   1. DEBUG：最详细的信息，包含完整的数据，生产环境禁止开启
   2. INFO：生产环境级别，包含基础数据信息，和完整的流程信息，能够描述出干了什么
   3. WARN：与预期不符的情况，但不影响结果，流程仍可以正常进行
   4. ERROR：错误，流程无法继续进行
   5. FATAL：禁用，不允许使用FATAL
6. 业务/系统日志的选择规则
   1. 业务Business：一个由用户触发的、可闭环的完整调用。强制带上Context，要求能用Context中的message-id过滤出本次调用的完整上下文信息。
      如：HTTP request，包含本次请求过程中框架收到信息、参数处理结果、实际调用函数结果、数据库增删改查等，都用同一个Context打到Business日志里。
   2. 系统System：后台触发的，或是较底层、通用的处理流程。
      如：定时清理任务、定时同步任务、自动检查、自动状态回写等
   原则上，当系统没有人使用的时候，是不应该有business日志的。

## 演进方向
1. 精确界定Business和System的区别规范
2. 精确打日志的时机和频率

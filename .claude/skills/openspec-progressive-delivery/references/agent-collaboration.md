# Agent 协作指南

本文档定义渐进式提案实施过程中多 Agent 的协作模式。

## 概述

大规模变更需要多个 Agent 协作完成，每个 Agent 负责特定职责。通过明确的角色分工和通信协议，确保：

- ✅ 任务分解清晰，职责明确
- ✅ 并行执行提升效率
- ✅ 失败隔离，问题可追溯
- ✅ 进度可视化，状态同步

---

## Agent 角色定义

### 1. Master Agent (主控)

**职责**: 任务分解、调度、进度追踪、最终决策

**能力**:
- 读取提案文档 (proposal.md, tasks.md)
- 分解任务为可执行单元
- 调度 Sub Agent 执行任务
- 汇总结果，更新进度
- 处理失败和冲突

**工具**:
- `TodoWrite` - 任务追踪
- `Read` - 读取文档
- `Task` - 调度 Sub Agent

**典型操作**:
```markdown
1. 读取 tasks.md 获取任务列表
2. 按阶段顺序分配任务
3. 调度 Sub Agent 执行
4. 等待结果，更新进度
5. 决定下一步行动
```

---

### 2. Research Agent (研究)

**职责**: 代码分析、影响评估、信息收集

**能力**:
- 分析代码结构和依赖
- 评估变更影响范围
- 收集技术信息
- 生成分析报告

**工具**:
- `mcp__serena__get_symbols_overview` - 文件概览
- `mcp__serena__search_for_pattern` - 模式搜索
- `mcp__serena__find_symbol` - 符号查找
- `mcp__serena__find_referencing_symbols` - 引用查找

**典型任务**:
```markdown
**任务**: 分析 GetRelayInfo 的使用范围

**执行**:
1. 使用 find_referencing_symbols 查找所有引用
2. 使用 search_for_pattern 搜索相关模式
3. 统计影响文件数和调用次数
4. 生成影响分析报告
```

**输出格式**:
```markdown
## 影响分析报告

### 搜索结果
- 函数: GetRelayInfo
- 引用数: 12
- 影响文件: 8

### 文件列表
| 文件 | 调用次数 | 风险等级 |
|------|----------|----------|
| pkg/workflow/node_install.go | 3 | 中 |
| pkg/workflow/node_uninstall.go | 2 | 低 |
...

### 建议
- 优先迁移高风险文件
- 注意循环依赖问题
```

### 4. Implementation Agent (实施)

**职责**: 代码修改、单元迁移、功能实现

**能力**:
- 执行代码修改
- 迁移单个单元
- 添加新功能
- 处理编译错误

**工具**:
- `mcp__serena__replace_symbol_body` - 替换符号
- `mcp__serena__insert_after_symbol` - 插入代码
- `Edit` - 文件编辑
- `Bash` - 编译验证

**典型任务**:
```markdown
**任务**: 迁移 NodeInstallWorkflow.Execute

**执行**:
1. 使用 find_symbol 读取当前实现
2. 使用 replace_symbol_body 替换实现
3. 运行 make build 验证编译
4. 报告完成状态
```

**输出格式**:
```markdown
## 实施报告

### 任务
迁移 NodeInstallWorkflow.Execute

### 修改
- 文件: pkg/workflow/node_install.go
- 行数: 45-78
- 变更: GetRelayInfo → GetRelayListByFilter

### 验证
- 编译: ✅ 通过
- 测试: ✅ 通过

### 状态
✅ 完成
```

## 通信协议

### 状态同步

使用共享状态文件同步 Agent 间的信息：

**文件**: `openspec/changes/<change-id>/.agent-state.json`

```json
{
  "change_id": "remove-relayinfo-cache",
  "current_phase": 3,
  "current_task": "3.2",
  "status": "in_progress",
  "agents": {
    "master": { "status": "waiting", "last_action": "dispatched task 3.2" },
    "implementation": { "status": "working", "task": "3.2" },
    "review": { "status": "idle" }
  },
  "completed_tasks": ["1.1", "1.2", "2.1", "3.1"],
  "pending_tasks": ["3.2", "3.3", "3.4"],
  "errors": [],
  "last_updated": "2024-01-15T10:30:00Z"
}
```

### 消息格式

Agent 间通过结构化消息通信：

**任务分配消息** (Master → Sub Agent):
```markdown
## 任务分配

**任务 ID**: 3.2
**类型**: implementation
**描述**: 迁移 NodeInstallWorkflow.Execute 到新的 relay 查询
**优先级**: 高
**依赖**: 3.1 (已完成)

**输入**:
- 源文件: pkg/workflow/node_install.go
- 目标方法: Execute
- 新 API: dao.GetRelayListByFilter

**期望输出**:
- 代码修改完成
- 编译通过
- 实施报告

**超时**: 10 分钟
```

**结果报告消息** (Sub Agent → Master):
```markdown
## 任务结果

**任务 ID**: 3.2
**状态**: ✅ 成功
**耗时**: 5 分钟

**结果**:
- 修改文件: pkg/workflow/node_install.go
- 变更行数: 15
- 编译状态: 通过

**产出物**:
- 实施报告已生成

**下一步建议**:
- 执行代码审查 (Review Agent)
- 然后进行任务 3.3
```

## 执行流程

### 标准执行流程

```
┌─────────────────────────────────────────────────────────────┐
│                    Master Agent                              │
│  1. 读取任务列表                                              │
│  2. 选择下一个待执行任务                                       │
└───────────────────────────┬─────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                   Research Agent                             │
│  3. 分析任务涉及的代码                                        │
│  4. 评估影响范围                                              │
│  5. 生成分析报告                                              │
└───────────────────────────┬─────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                 Implementation Agent                         │
│  6. 执行代码修改                                              │
│  7. 验证编译通过                                              │
│  8. 生成实施报告                                              │
└───────────────────────────┬─────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                    Review Agent                              │
│  9. 执行代码审查                                              │
│  10. 检查规范遵守                                             │
│  11. 生成审查报告                                             │
└───────────────────────────┬─────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                 Verification Agent                           │
│  12. 运行测试                                                 │
│  13. 验证功能                                                 │
│  14. 生成验证报告                                             │
└───────────────────────────┬─────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                    Master Agent                              │
│  15. 汇总结果                                                 │
│  16. 提交代码 (如果所有检查通过)                               │
│  17. 更新进度，进入下一个任务                                  │
└─────────────────────────────────────────────────────────────┘
```

### 并行执行流程

当任务之间无依赖时，可以并行执行：

```
                    Master Agent
                         │
           ┌─────────────┼─────────────┐
           │             │             │
           ▼             ▼             ▼
      Task 3.2      Task 3.3      Task 3.4
    (Workflow A)  (Workflow B)  (Workflow C)
           │             │             │
           └─────────────┼─────────────┘
                         │
                         ▼
                  Master Agent
               (汇总并行结果)
```

**并行执行规则**:
1. 同一阶段内的独立单元可以并行
2. 不同阶段必须顺序执行
3. 有依赖关系的任务必须顺序执行
4. 最多同时运行 3 个 Sub Agent

## 失败处理

### 失败类型与处理策略

| 失败类型 | 影响 | 处理策略 |
|----------|------|----------|
| 编译失败 | 阻塞 | 立即停止，修复后重试 |
| 测试失败 | 阻塞 | 分析失败原因，修复或回滚 |
| 审查不通过 | 阻塞 | 修复问题，重新审查 |
| 超时 | 可恢复 | 检查进度，决定续继或中止 |
| Agent 崩溃 | 可恢复 | 重启 Agent，从检查点恢复 |

### 失败处理流程

```
┌─────────────────────────────────────────────────────────────┐
│                      检测到失败                              │
└───────────────────────────┬─────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                   记录失败信息                               │
│  - 失败类型                                                  │
│  - 错误消息                                                  │
│  - 当前状态                                                  │
└───────────────────────────┬─────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                   评估失败影响                               │
│  - 是否可恢复?                                               │
│  - 是否需要回滚?                                             │
│  - 是否需要人工介入?                                          │
└───────────────────────────┬─────────────────────────────────┘
                            │
              ┌─────────────┼─────────────┐
              │             │             │
              ▼             ▼             ▼
         可恢复          需回滚        需人工
           │               │             │
           ▼               ▼             ▼
        修复重试      git reset      暂停等待
                       HEAD~1
```

### 检查点机制

每个任务完成后创建检查点，支持从失败点恢复：

```json
{
  "checkpoint_id": "cp-20240115-103000",
  "task_id": "3.2",
  "status": "completed",
  "git_commit": "abc123",
  "files_modified": [
    "pkg/workflow/node_install.go"
  ],
  "timestamp": "2024-01-15T10:30:00Z"
}
```

**恢复策略**:
1. 从最近的成功检查点恢复
2. 重新执行失败的任务
3. 跳过已完成的步骤

## 最佳实践

### 1. 任务分解原则

- ✅ 每个任务单一职责
- ✅ 任务粒度适中 (5-15 分钟)
- ✅ 任务间依赖清晰
- ✅ 每个任务有明确的验收标准

### 2. Agent 调度原则

- ✅ 优先串行执行，降低复杂度
- ✅ 仅在任务独立时并行
- ✅ 限制并行数量 (≤ 3)
- ✅ 设置合理超时

### 3. 通信原则

- ✅ 消息格式标准化
- ✅ 状态及时同步
- ✅ 错误信息详细
- ✅ 进度可追溯

### 4. 失败处理原则

- ✅ 快速失败，立即处理
- ✅ 保留现场，便于分析
- ✅ 从检查点恢复
- ✅ 必要时人工介入

## 常见问题

### Q1: 如何决定任务是否可以并行?

**答案**: 检查以下条件：
1. 任务修改不同的文件
2. 任务之间无数据依赖
3. 任务在同一阶段内
4. 并行数量不超过 3

### Q2: Sub Agent 超时怎么处理?

**答案**:
1. 检查 Agent 状态
2. 如果仍在运行，等待或增加超时
3. 如果已崩溃，从检查点恢复
4. 记录超时原因，调整后续任务超时设置

### Q3: 如何处理 Agent 间的冲突?

**答案**:
1. 避免并行修改同一文件
2. 使用锁机制防止并发写入
3. 发生冲突时，以 Master Agent 决策为准
4. 记录冲突，后续任务分解时避免

### Q4: 如何确保 Agent 协作的一致性?

**答案**:
1. 使用共享状态文件
2. 每个 Agent 完成后更新状态
3. Master Agent 定期同步状态
4. 使用版本号防止状态覆盖

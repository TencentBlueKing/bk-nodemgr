# 架构与设计原则审查指南

本文档提炼自团队 Golang 最佳实践和 CR 案例集，面向 reviewer 提供可操作的架构设计检查清单。

每条原则标注了与 `AGENTS.md` 条目的映射关系——带 `[AGENTS]` 标记的项在 AGENTS.md 中有对应强约束。

---

## 一、结构与耦合

### 1.1 DRY — 不要重复

一处知识在系统中只应有唯一、明确的表示。

**审查要点：**
- 新增代码是否与已有代码存在功能重叠？（用 `serena.find_symbol` + `substring_matching` 搜索相似函数）
- 是否可以复用已有 helper、proto 转换函数、DAO 方法？
- 同一段逻辑是否在多处出现，应抽取为共享函数？

**`[AGENTS]` 映射：** "prefer extending existing code paths/helpers/proto conversions over parallel implementations"

**坏味道：** 新建了 `convertProtoToFoo()` 但 `pkg/proto/` 已有功能相同的转换函数。

### 1.2 正交性 — 消除不相关事物的影响

模块之间不应产生不必要的隐式耦合。

**审查要点：**
- 是否引入了不必要的包级全局变量？
- 修改某个模块时，是否需要同时修改不相关的模块？
- 是否因复用一小段代码而引入了整个包的依赖？

**`[AGENTS]` 映射：** "do not place service-specific logic in pkg when it belongs in internal/\<service\>"

**坏味道：** `pkg/` 中出现了仅被 `internal/backend/` 使用的函数。

### 1.3 依赖方向正确 (DIP)

依赖应从具体到抽象，`internal` 依赖 `pkg`，而非反向。

**审查要点：**
- `pkg/` 是否 import 了 `internal/` 下的包？（严重违反 ❌）
- 是否面向 interface 编程而非依赖具体 struct？
- proto struct 是否在 `pkg/proto/` 层转换后才进入业务逻辑？

**`[AGENTS]` 映射：** "treat proto structs as boundary types and convert via pkg/proto/* before business logic"

### 1.4 组合优于继承

Go 天然倾向组合（embedding），但仍需警惕过度嵌套的 struct embedding。

**审查要点：**
- 是否通过 embedding 引入了不需要的方法集？
- 是否可以用 interface + 组合替代深层嵌套？

## 二、函数与抽象层级

### 2.1 单层级原则 — 函数只包含一个抽象层级

一个函数体内不应同时出现高层业务编排和底层实现细节。

**审查要点：**
- 函数是否在做业务流程编排的同时包含了具体的字段赋值/循环/格式化？
- 是否可以将底层细节抽取为子函数，让顶层函数只做"调度"？
- 函数行数超过 80 行时，是否可以按抽象层级拆分？

**好的例子：** 顶层函数只调用 `checkCookie()`, `getRelationship()` 等子函数，不展开细节。

### 2.2 只管命令不要询问

调用方应该给对象发送命令，而不是先查询对象内部状态再决定做什么。

**审查要点：**
- 是否先 Get 再 Set 同一对象的字段？（应合并为一个方法）
- 是否暴露了不必要的内部细节给调用方？

### 2.3 传入最小参数集

函数应该接收它关心的最小数据集合，而非整个大 struct 后从中取一两个字段。

**审查要点：**
- 函数参数是否过于"宽泛"（传了一整个 struct，但只用了其中一个字段）？
- 链式调用 `a.B.C.D` 暴露了多少层内部结构？

### 2.4 契约式设计

函数的输入输出契约应简洁、明确。

**审查要点：**
- 函数做的事情是否不多不少刚好匹配其名称暗示的契约？
- 参数和返回值的类型是否足以表达契约（而非依赖隐式约定）？

## 三、错误与日志

### 3.1 尽早崩溃 — 不要掩盖问题

程序应在问题出现时立即暴露，而非隐藏后继续运行。

**审查要点：**
- 是否有 `recover()` 后什么都不做的代码？（毒瘤 ❌）
- 错误是否被静默忽略（`_ = someFunc()` 且无注释说明原因）？
- 是否该 return error 的地方只打了日志就继续执行？

### 3.2 错误传递 — Error Wrapping

错误信息应该跨层级传递，中间层不关心可以 wrap 后透传。

**审查要点：**
- 是否使用 `fmt.Errorf("...: %w", err)` 包装？
- 错误消息是否提供了足够上下文，让上层能定位问题？
- 是否丢弃了底层错误信息（用 `errors.New` 替代了 wrap）？

> 此项已在 `go-standards.md` 中有详细规范，此处强调设计意图。

### 3.3 缄默原则 — 不过度日志

正常流程不应产生大量日志，否则错误信息会被淹没。

**审查要点：**
- 正常（非错误）路径是否打了不必要的 Info/Debug 日志？
- 调试日志是否应该降级或在提交前移除？
- 循环体内是否有高频日志？

**`[AGENTS]` 映射：** "use pkg/logger for structured logging"（确保走统一框架，便于级别控制）

## 四、显式与一致

### 4.1 所有细节显式处理

不给后续维护者留下"这是设计如此还是遗漏"的疑问。

**审查要点：**
- 忽略返回值时是否使用了 `_ = F()` 而非裸调用 `F()`？
- 空实现是否有注释说明"空实现即为完整实现"？
- shadow write：`:=` 是否意外遮蔽了外层变量？

### 4.2 统一术语

项目中同一概念使用统一名称。

**审查要点：**
- 新增的类型/变量命名是否与已有约定一致？
- 是否存在对同一概念使用不同名称的情况？

### 4.3 不写死可变值

IP、端口、路径等可变值不应硬编码。

**审查要点：**
- 是否有硬编码的 IP 地址、端口号、文件路径？
- 是否有应该使用常量/配置但直接使用字面量 `1, 2, 3` 的情况？

## 五、可逆性与熵控制

### 5.1 可逆性 — 假设决定会变

设计应尽可能不绑死在某个具体选择上。

**审查要点：**
- 是否直接依赖了某个特定环境/平台的 API，而非通过抽象层？
- 是否因为"当前只有一种情况"就省略了扩展点？

### 5.2 控制熵 — 遵循项目既定范式

对同一类问题应始终使用项目规范的范式解决，不要引入新的不同范式。

**审查要点：**
- 新代码的实现方式是否与同层级/同模块的已有代码一致？
- 是否引入了"另一种方式做同样的事情"？
- 是否有 hardcode / 特殊逻辑可以用通用范式替代？

**`[AGENTS]` 映射：** "before coding read relevant module + at least one analogous implementation in same service/layer"

---

## 审查时的使用方式

1. **步骤 2（Design 审查）** — 重点检查第一节（结构与耦合）和第五节（可逆性与熵控制）
2. **步骤 5（一致性检查）** — 重点检查第四节（显式与一致）
3. **步骤 6（质量检查）** — 重点检查第二节（函数与抽象层级）和第三节（错误与日志）

标记为 `[AGENTS]` 的项，违反时升级为 ⚠️ 重要问题或 ❌ 严重问题（取决于 AGENTS.md 原文措辞强度——"never" / "do not" 开头的为阻塞性）。
